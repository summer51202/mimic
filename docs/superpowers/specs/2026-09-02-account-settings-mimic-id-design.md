# Account Settings and Mimic ID Design

**Date:** 2026-09-02  
**Status:** Approved for implementation planning

## Goal

Add a real authenticated Settings destination where a user can view account information, edit only their display name, copy a stable public identifier, and sign out. Make group members distinguishable even when display names change by showing the same immutable public identifier in the member roster.

## Confirmed Product Decisions

- Every account receives a dedicated public `Mimic ID` separate from the internal user UUID.
- The visible format is `MIMIC-XXXX-XXXX` using uppercase, unambiguous letters and digits.
- Mimic ID is generated by the service, protected by a database unique constraint, and never editable.
- Display name remains editable and is not an identity key.
- Settings displays email and Mimic ID as read-only account information; locale and timezone are not editable in this slice.
- Settings provides the existing session-clearing logout behavior.
- Group member rows display both the current display name and stable Mimic ID.

## Scope

### Included

1. Add and backfill `users.mimic_id` with a unique, non-null database constraint.
2. Generate a Mimic ID when registering a new account, retrying a bounded number of times if the database reports a unique collision.
3. Return `mimic_id` from `GET /me`, profile-update responses, authentication user payloads, and group-member responses.
4. Add a protected `/app/settings` page and activate the existing Settings navigation item.
5. Show read-only email and Mimic ID, with an explicit Copy ID action.
6. Allow editing only `display_name` through the canonical `PATCH /me` endpoint.
7. Provide Sign out and redirect to `/login` after the local browser session is cleared.
8. Display Mimic ID in the group member roster.

### Excluded

- Editable email, password changes, locale, timezone, avatar, notification preferences, or account deletion.
- Searching for users by Mimic ID, direct invitations by Mimic ID, or using Mimic ID as an authorization key.
- Replacing internal UUID foreign keys or JWT subjects.
- Group archive/delete behavior and QR invitation support.
- Showing Mimic ID in every financial position list; the authoritative identity view for this slice is the group member roster.

## Mimic ID Contract

The canonical representation matches:

```text
^MIMIC-[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]{4}-[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]{4}$
```

The alphabet excludes `0`, `1`, `I`, and `O` to reduce transcription errors. Eight base-32 characters provide approximately 1.1 trillion candidates. The value is public and stable, but it is not a secret, login credential, or authorization token.

The service uses cryptographically secure random bytes to choose characters. A unique database index is authoritative. Registration retries generation only for a `mimic_id` unique collision and surfaces an operational failure after a small fixed retry limit; email conflicts retain their existing error behavior.

The migration assigns existing users valid IDs before setting the column to `NOT NULL`. Backfill is performed in SQL and must produce one unique value per existing row without changing user IDs, membership history, or audit records.

## Backend Architecture

### Data model

`User` gains:

```prisma
mimicId String @unique @map("mimic_id") @db.VarChar(15)
```

Internal relations continue using `User.id`. No client input DTO accepts `mimic_id`.

### Generation boundary

A focused users-module utility owns format generation and validation constants. `UsersService.createUser()` assigns the value and owns collision retry behavior because it already owns user persistence. Tests inject or mock generated candidates so collision behavior is deterministic.

### API mapping

The following response objects gain `mimic_id`:

- authentication register/login/refresh `user` payloads;
- `GET /me`;
- `PATCH /me` and temporary `POST /me` compatibility responses;
- `GET /groups/:groupId/members`;
- member returned by `PATCH /groups/:groupId/members/:userId`.

Requests never accept a Mimic ID update. Existing `id` fields remain for compatibility and internal client reconciliation.

## Web Architecture

### Read path

The Settings page is a protected App Router page under the existing authenticated layout. A focused settings query calls the backend `GET /me` through `authenticatedServerApi`, validates the response with a Zod profile schema, and passes the profile to the client form. Read failures use the existing `AppReadFailure` boundary.

### Mutation path

Add `/api/app/me` as the cookie-backed BFF boundary:

- `GET` is not required because the server component reads directly through the authenticated server API.
- `PATCH` validates CSRF, forwards only `display_name` with the access token, and returns the normal data envelope.

The existing generic authenticated client mutation helper moves from the groups feature into shared API infrastructure so Settings, groups, and invitations use the same CSRF and one-shot refresh behavior without cross-feature imports.

The form trims the display name, validates 1–100 characters, preserves the entered value after failure, disables duplicate submission while pending, and updates its displayed saved state after success.

### Logout path

Sign out uses the existing `/api/auth/logout` route with CSRF protection. That route continues clearing access, refresh, and CSRF cookies even when the backend logout call is unavailable. After a successful local response, the client navigates to `/login`. A failed local request keeps the user on Settings and presents an actionable retry message.

### Navigation and presentation

- The current disabled Settings navigation item becomes an available link to `/app/settings`.
- `/app/settings` participates in current-section highlighting on mobile and desktop.
- The page follows the existing PixelFrame, PixelField, PixelButton, and PixelNotice visual language.
- Account information presents display name, email, and Mimic ID with long-text containment.
- Copy ID uses `navigator.clipboard.writeText`; if unavailable, the rendered Mimic ID is focused and selected for manual copying.
- Member roster rows render the Mimic ID under the display name and role without changing member actions or authorization.

## Data Flow

### Settings load

1. Authenticated layout verifies a session.
2. Settings server page requests `GET /me` with the access token.
3. The response schema validates `id`, `mimic_id`, email, display name, locale, and timezone.
4. The page renders the client form inside the existing pixel UI.

### Display-name update

1. User edits the display-name field and submits.
2. Client validation trims and checks the value.
3. Shared authenticated fetch obtains CSRF and sends `PATCH /api/app/me`.
4. The BFF validates CSRF and forwards `PATCH /me` with only `display_name`.
5. The returned profile replaces the form's saved state and a success notice is announced.

### Logout

1. User explicitly activates Sign out.
2. The client posts to `/api/auth/logout` through the authenticated mutation helper.
3. The BFF clears browser session cookies regardless of backend logout availability.
4. The browser navigates to `/login`.

## Error Handling

- Invalid or blank display names receive a field-local message and focus remains on the editable field.
- A second click while an update or logout is pending does not send a duplicate request.
- Session expiry uses the existing one-shot refresh path; explicit rejection tells the user to sign in again.
- Backend validation and operational failures preserve the current form value.
- A profile read contract failure or outage uses the established authenticated read failure UI.
- Clipboard absence is not an error; manual selection is provided.
- Mimic ID generation never silently falls back to the internal UUID.

## Testing Strategy

### Backend

- Unit tests for format generation and allowed alphabet.
- Users service tests for assignment, unique-collision retry, retry exhaustion, and unchanged email-conflict behavior.
- Users e2e controller tests asserting `mimic_id` in read and update envelopes and proving update input cannot change it.
- Auth tests asserting register/login/refresh user payloads include `mimic_id`.
- Group tests asserting member responses include `mimic_id`.
- Prisma migration contract checks for non-null and unique `mimic_id`.

### Web

- Schema and query tests for the profile response.
- BFF tests for CSRF rejection, exact PATCH forwarding, envelope response, and backend errors.
- Settings form tests for initial account information, trimmed display-name update, duplicate-submit locking, failure preservation, Copy ID, manual selection fallback, and logout redirect.
- Route-boundary tests for successful Settings rendering and read failures.
- Navigation tests for active Settings links on mobile and desktop.
- Member roster tests for stable Mimic ID rendering and text containment.
- Full lint, typecheck, unit/integration test, and production build verification.

## Rollout and Compatibility

The schema migration must run before deploying code that requires `mimic_id`. Existing internal IDs, JWT subjects, membership foreign keys, API `id` fields, and temporary `POST /me` compatibility remain unchanged. Mobile clients may ignore the additive response field.

## Follow-ups

After this slice, the next planned independent feature is safe archive for a single-owner group with no financial history. Search/invite by Mimic ID, QR invitation entry, account deletion, and broader profile preferences remain separate decisions.
